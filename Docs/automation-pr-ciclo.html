Pull requests

Una automatización vigila los pull requests

Usa la API de tu propio micrositio de administración como plano de soporte.

El ciclo

  1. 1

    Un pull request se abre o se actualiza.

  2. 2

    La automatización llama a la API del micrositio.

  3. 3

    El micrositio trae el issue de Sentry relacionado (release, stack, conteo) y lo adjunta al registro de soporte.

  4. 4

    El agente pide a la API cada clave de Jira nombrada en los encabezados del mensaje de commit de ese pull request.

  1. 5

    La API devuelve un solo JSON estructurado: claves de Jira, resumen del issue y criterios de aceptación.

  2. 6

    El agente compara el diff con la rama de origen de la que se cortó la tarea, no con una rama cualquiera.

  3. 7

    Revisión estática: el diff satisface cada criterio de aceptación de esa historia o issue de Jira.

  4. 8

    El resultado queda en el comentario del pull request y en el registro de soporte del micrositio. Una persona sigue aprobando.

Sentry queda detrás del micrositio

  • El agente llama a un solo sistema: la API del micrositio.
  • Sentry no es una segunda bandeja.
  • El micrositio guarda el enlace, el release y el conteo.
  • El stack completo no se copia en su base de datos.

Lo que recibe el agente

Contrato. Un solo objeto.

{
  "pr": 128,
  "baseBranch": "linea-origen",
  "jiraKeys": ["PLAT-18"],
  "issues": [
    {
      "key": "PLAT-18",
      "summary": "El registro de soporte conserva el release",
      "acceptanceCriteria": [
        "Guarda el enlace al issue",
        "Guarda el release y el conteo"
      ]
    }
  ],
  "sentry": {
    "issueUrl": "https://sentry.example/issues/1001",
    "release": "admin@1.4.2",
    "count": 17
  }
}

La revisión estática

El diff del pull request se compara con baseBranch, la rama de origen de la tarea.

  • Pasa El criterio se cumple en el diff.
  • Falla El diff no cumple el criterio.
  • No se ve en el diff El criterio no aparece en el cambio.

Sin merge automático.
